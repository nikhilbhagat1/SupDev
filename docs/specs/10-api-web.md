# 10 API & web UI (board, ticket chat, Jira)

**Purpose** Deliver the engine as REST + SSE with a Jira-style Kanban board, a per-ticket chat panel and Settings.

**API** (`api/app.py`; admin endpoints are in spec 11)
- Identity/meta: `GET /api/auth/mode`, `GET /api/me`, `GET /api/modes` (modes from the plugin registry, with labels), `GET /api/plugins`, `GET /api/health`.
- Sessions: `POST/GET /api/sessions`, `GET /api/sessions/{id}` (phase data, pending approvals with exact content/hash/roles/`can_approve`, evidence, requirements, budget), `POST …/messages` (SSE), `POST …/continue` (SSE), `POST …/approvals/{aid}/grant` (role-checked, optional `seen_hash`), `POST …/mode`, `POST …/resume/{wid}`, `POST …/budget`. Per-session lock.
- Board/Jira (read-only unless noted; tenant's own Jira integration; cached 60 s; external free text redacted): `GET /api/board?mode=` (phases, cards, backlog, configured issue types, mode label), `GET /api/issues` (stories/tasks/bugs + the board's real columns + `epics` + per-user `can_move`), `GET /api/releases`, `GET /api/releases/{id}/issues`, **`POST /api/issues/{key}/move`** (write: a human's Jira workflow transition, see below), `GET /api/audit` (lead/admin/sre).
- Auth via the `Authenticator` plugin (`dev-header` locally, `token` for shared use). UI files are served `Cache-Control: no-cache` so a stale `index.html` never pairs with a new `app.js`.

**UI** (`web/`, work-management layout with its own branding; light/dark; no build step; all dynamic content via the `h()` DOM builder — no innerHTML). Top nav **Board · Settings**, a mode toggle built from `/api/modes`, **＋ Create**, avatar menu (identity/token, sign out).
- **Nothing about your workflow is hardcoded:** mode names come from the registry; issue types, statuses and columns come from Jira; colours are derived from names, so custom types/modes just work.
- **Board (per mode).** Cards are the Jira tickets fetched read-only: newest first; open tickets plus those updated in the last 14 days; **epics and sub-tasks are never shown** (and work items opened on an epic are hidden too). Two groupings:
  - **Jira status** (default when Jira is connected): columns = the Jira board's real columns (Agile board config; else workflow statuses ordered new → in progress → done). **Drag a card, or use its ⋯ Move menu (keyboard/touch), to change its status in Jira.** The move is a Jira *workflow transition* by the signed-in human: allowed for roles that may approve `ticket_status`, only for tickets of the configured project, audited (`ui_ticket_move`); a disallowed move is refused with the allowed next statuses and the card snaps back. Chats/work items without a ticket sit in a "Supdev only" column (last).
  - **Supdev phase**: read-only columns = workflow phases (Backlog + the mode's phases); Jira tickets show their Jira status.
  - **Sync:** auto-refresh every 45 s while open, **↻ Sync**, after every move and when the agent syncs a status; "Synced 12 s ago". Jira is the source of truth for status.
  - **Filters (reset on every visit):** **Release** — a plain dropdown of release names; filters by ticket key via `GET /api/releases/{id}/issues` (JQL `fixVersion = <numeric id>`, id validated as digits) **plus tickets under any epic that carries the release** (`via_epics`; the board says "includes work under epic X"; `parent in (…)`, with `"Epic Link"` fallback for classic projects). **Types** — toggle chips with counts for every issue type the project has; an admin can set each board's default set in Settings → Board (`board.types`).
  - **Releases panel** (right): unreleased first with due date, overdue flag and progress; recently released; "Filter board" per release; ↻ refresh; helpful empty/not-connected states.
- **Ticket chat panel (left).** Clicking a card opens that ticket's panel next to the board (✕ closes; switching mode closes; the open ticket is remembered across reloads). Every ticket/work item has its **own chat session and its own details** — nothing is shared. Header: type, key (link to Jira), title, Jira status, mode, phase and approval badges, phase progress bar. One view, no tabs: a collapsible **Ticket details** section (Jira fields; Supdev mode/phase/session/budget; requirements for DEV or evidence for SUPPORT; parked items) — open until work starts, then collapsed — above the always-visible conversation (activity feed with gate/denied/flag/Jira-sync events, "Action required" approval cards showing the exact artifact + hash) with the composer pinned at the bottom.
- **Start / Continue.** An unstarted ticket card has a primary **Start** button: it creates that ticket's work item (ref = ticket key) and chat, opens the panel and sends "Start work on KEY: title" so the agent begins intake and clarification. Started tickets show **Continue**. **＋ Create** makes a manual work item and opens it in the same panel.
- **Agent → Jira status.** Separate from drag-to-move: with the tenant's opt-in **Jira status sync** (spec 04/11) the engine moves the ticket when the agent advances a phase; the panel shows "Jira KEY: To Do → In Progress" and the card moves. Anything else the agent writes still needs an approval bound to the exact artifact.
- **Settings**: left-nav sections (spec 11).

**Verification status** Checked by hand in Chrome (board in both groupings, filters, Start, ticket panel, Create dialog, Settings, custom-vocabulary Jira mock, an end-to-end agent→Jira status sync against a mock Jira with a real workflow, and the release filter against a real Jira project). Drag-and-drop was verified by dispatching `DragEvent`s (the automation tool's mouse cannot start native HTML5 drags) plus real clicks on the Move menu; a real-mouse drag has not been automated.
**Test gaps** No automated browser tests; board is own-sessions only (no team-wide view); SSE `continue`; audit endpoint role gate; budget endpoint; concurrent messages to one session; the SSE parser in `app.js`; phone layout.
**Out of scope** OIDC login, CSRF/session cookies, notifications, real-time push from Jira (polling only), drag between Supdev-phase columns (phases advance only through the gated workflow).
